# The personal-data surface — DERIVED candidates, DECLARED classifications.
#
# Under goal "A person can be erased without the ledger losing what happened".
#
# WHY THIS FILE EXISTS, AND WHY IT IS HALF A FILE.
#
# A fully-derived inventory of personal data is impossible: no query can tell you whether a `text`
# column holds a person's name. A fully-declared one rots — the way it rots is that someone adds a
# column and nobody remembers this file. So the work is split, and the split is the point:
#
#   * `personal_data_surface_test.rs` DERIVES the candidate set from the live catalog. It cannot
#     miss a column, because it asks Postgres rather than a person.
#   * This file DECLARES the judgement for each candidate: what class of personal data it holds and
#     how far erasure can reach it.
#   * The test fails on any derived candidate with no line here, and on any line here naming a
#     column that no longer exists. Neither half can drift silently.
#
# The derivations are seven, and each exists because the one before it is blind to something:
#
#   fk       foreign keys into kb_profiles / kb_entities.
#   poly     polymorphic (`*_table` + `*_id`) references, which carry NO foreign key at all —
#            Postgres will neither cascade them nor complain about them.
#   prin     every column of the principal tables themselves, where identity actually lives.
#   vec      vector / tsvector columns: representations derived from content.
#   json     every jsonb column, because that is where unbounded free-form data lives.
#   bytes    every bytea column. NO structural derivation above sees BYTEA — raw binary content
#            is invisible to type-keyed nomination alike, which is how staged upload bytes went
#            undeclared (review F3). Binary content is personal content the moment a person
#            uploads it, so every bytea column nominates.
#   named    a NAME-PATTERN heuristic over text columns. It is the only derivation that is not
#            structural, and it exists because four identifier columns have no structure to find
#            them by: kb_team_invitations.invited_email, kb_slack_link_intents.slack_principal_id,
#            kb_slack_grant_vault.slack_principal_id, kb_saml_idp.email_attr. A heuristic produces
#            CANDIDATES, never verdicts — which is exactly what this file is for.
#
# WHAT IS NOT COVERED, STATED SO NOBODY INFERS COVERAGE FROM SILENCE.
# The `text`/`varchar` columns no derivation above nominates are NOT classified here. They are
# declared in the sibling manifest, scripts/sensitivity-scan-surface.txt, which states their count
# and adjudicates each as scan / structural / credential / out-of-scope. The two files PARTITION
# every text/varchar column of a public base table (sensitivity_scan_surface_test.rs), so a column
# is never in neither. That is a declaration, not a detection: a column called `note` that happens
# to hold a person's name is found by no derivation here, and is reached only by the sensitivity
# sweep reading what the sibling marks `scan`.
#
# FORMAT (line-oriented; `#` comments and blank lines ignored)
#   <table>.<column> | <class> | <ceiling> | <achieved> | <note>
#
# class
#   identifier     a direct identifier of a natural person
#   reference      a pseudonymous UUID pointing at a principal
#   content        authored content
#   derived        a representation computed FROM content (vector, search index)
#   incidental     free-form that MAY carry personal data depending on what was written
#   discriminator  the table-name half of a polymorphic pair; no personal data, but it is what
#                  makes its `_id` sibling resolvable, so it is declared rather than skipped
#   none           carries no personal data
#
# ceiling — how far erasure reaches
#   full        erasable outright
#   recompute   must be RECOMPUTED after an erasure, not deleted; a cascade will not reach it
#   pseudonym   a UUID that stops identifying anyone once kb_profiles is tombstoned
#   none        on the append-only ledger; cannot be erased at all
#   n-a         nothing to erase
#
# achieved — what the person act DOES reach, which is not the ceiling. The ceiling says how far
# erasure could go. Until 2026-10-10 nothing recorded what the act achieved, and the ceiling was
# read as that: the act fully reached 9 of the then 27 `full` lines. Every `full` line names what
# reaches it, or the remainder; every other line carries `-`. Claims join with ` + `, and each one
# is bound by personal_data_surface_test.rs to the live act:
#   erased:<arm>         _erasure_apply_redaction assigns the column an erasure value in an UPDATE
#                        of its table, and every assignment to it erases (NULL, '', '{}', or an
#                        'erased…' sentinel, `v_sentinel` included)
#   deleted:<arm>        _erasure_apply_redaction deletes from the column's table
#   cascaded:<arm>:<t>   _erasure_apply_redaction deletes from <t>, and the column's table has a
#                        foreign key to <t> with ON DELETE CASCADE
#   resource-erasure:D2.<step>
#                        principal_erasure_execute runs resource_erasure_execute over the estate,
#                        which runs _resource_erasure_apply_redaction, and
#                        scripts/resource-erasure-surface.txt declares the column handled:D2.<step>
#   remainder: <reason>  the act does not reach it; the reason is required
#
# <arm> is the number in the act body's comments: (1) to (12), with 4a, 6a, 7a and 9a. It is a
# label for the reader, and the test checks only that it names an arm that exists.
#
# WHAT THE ACHIEVED BINDING DOES NOT SEE.
#   * Rows. A claim binds when the statement exists. Which rows its WHERE reaches is the act's own
#     witnesses' job; where the act leaves rows of a reached column, the note says which.
#   * Control flow. It binds statements, not the branches that run them: an UPDATE under an IF
#     never taken, or after a RETURN, still binds. The refresh-token claims are two branches of one
#     IF, and the fence sees both.
#   * Arms. Comments are dropped before binding, so it cannot tell which arm a statement sits in.
